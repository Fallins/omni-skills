# UI／UX 稽核

本技能只檢查與交報告，不修程式、不改資料、不自動開票、commit、push 或部署。若使用者只要求 UI 或 UX，另一軸標不適用或超出範圍，不強迫擴大。審核規格或程式變更本身另用 review-change。

1. **鎖定範圍**：指定 repo／commit 或可識別部署、角色、主要任務及裝置。讀適用規則與設計來源；若已確認 Agent Work 對應專案，載入該專案的選填 `ui-ux-audit-profile.md`。沒 profile 先由 repo 規則和任務目標推導本次準則，列出假設。Profile 不是操作授權。
2. **先判斷能否安全操作**：確認站點、依賴、帳戶與實際副作用。開頁也可能寫閱讀進度、排工作、發通知或觸發預載。正式環境只做已確認不會改產品狀態且不觸發外部動作的路徑；不確定就用已授權隔離環境與測試資料。沒有安全環境就做靜態檢查並標明不可實測，不換個 URL 當成隔離。
3. **取得地圖**：依 [FeatureMap 查找規則](../feature-map/references/storage.md)用文件、程式與既有證據找本範圍的現有地圖；此階段不操作產品入口。可用就引用 ID 與來源；只有部分／過時只補本次缺口，不改原檔。缺少可用的範圍地圖時，在**同一個 session** 讀取並依 [feature-map](../feature-map/SKILL.md) 做最小暫時盤點，不開另一個 agent、流程或額度任務。以宿主實際載入的 skill 來源解析同一安裝根與版本（必要時循已知連結解出其真實目錄），不可用 CWD、任意家目錄或不同版本替代。若 skill 或契約無法解析，從已授權來源就地列入口、任務、角色、狀態與未知；在報告標明 fallback 和原因，不宣稱已執行 sibling 或已建正式 map。存在兩份相衝突時保留來源差異，不選新正式來源。
4. **分開 UI 和 UX 找證據**：在操作前再確認該路徑及其自動請求皆符合安全條件；可安全實測時，先以使用者目標走一遍，不先把內部模組設計當成使用者的心智模型；再用程式、共用元件和規則定位原因。兩軸方法與適用性見[稽核準則](references/checks.md)。
5. **交付報告**：依[報告格式](references/report.md)列出實看、模擬、靜態、未驗證及不適用的覆蓋，分別標記問題性質、影響與證據。寫檔只用已獲授權且確認的報告位置；本次地圖預設只留在報告或對話，不同時建兩份。提出優先修正與驗收方式後停止。
