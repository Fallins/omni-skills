# 大型任務協作

主代理擔任 planner / integrator：掌握需求、判斷證據、設計接口、分派工作、審查與整合。子代理負責有邊界、可驗收的調查、實作或審查；不要只轉交整份需求後等待回報。

## 1. 啟動與能力確認

- 辨識本輪目標、範圍與授權。只有「大型任務模式」或只有規劃要求時，預設 plan-only：讀取、查核、提出方案，不改產品程式碼、不部署。使用者已明確要求「規劃並執行」時，完成必要查核及下述分析確認關卡即可依授權繼續，不另加一個重複的批准關卡。具體高風險操作仍遵守執行環境的確認要求。
- 缺少任務內容、資料或 repo 時，先問最小必要問題；不要憑空建立規格。技能的關鍵字是啟用慣例，不代表已替使用者安裝全域觸發器。
- 先做 capability preflight：確認可用環境、repo／版本、讀寫權限、測試工具、代理工具、並行上限，以及模型與 reasoning effort 的實際支援情況。遵守宿主環境的模型與委派限制。
- 工作流選項：executor_preference 預設保留「Luna MAX」；model_selection 可設為 ask_once（預設）或 default。這是子代理偏好，不變更主代理模型，也不是供應商 API 設定。使用者明確指定的模型／effort 優先；記錄偏好來源與有效範圍，同一任務續作沿用已確認選擇，不自行寫入全域設定。
- 只有準備實際委派且環境允許時才處理模型選擇；純規劃且不委派時記為 not applicable。ask_once：若本任務尚未指定或確認，只問一次：「本輪子代理預設用 Luna MAX；要沿用，還是改成其他模型與推理強度？」已有明確選擇不重問。default：沿用仍適用的已確認偏好；沒有確認紀錄時回到 ask_once。等待選擇期間，可繼續不依賴該選擇、且符合任務授權與分析確認關卡的工作；不能先用其他模型派工。
- 「Luna MAX」只是偏好別名，不是 API ID。由目前工具能力或適用的官方文件驗證 model 與 effort 的映射，記錄 requested alias、resolved model、resolved effort 與證據。若有多個 Luna 版本且沒有已確認的版本，或 MAX 的映射不明，列出可用組合讓使用者決定，不自行挑最新版。工具無法選模型、無法核實映射或組合不可用時，提出實際可用的替代方案；不可靜默降級或聲稱已符合偏好。未回覆不等於同意；此阻礙只阻擋需要該選擇的委派。
- 無子代理工具、委派受限或無可用名額時，明確記錄能力限制。若使用者只要求成果且已授權實作，主代理可依相同 task contracts 循序執行，保留 Luna MAX 作為未來委派偏好，實際執行者與模型如實記錄；不得宣稱已使用 Luna MAX 或獨立代理。若使用者明定必須由指定子代理／模型執行，則暫停相應實作，交付可完成的規劃並提出替代選項，待明確選擇後續做。只有 plan-only 授權時仍只做規劃。

## 2. 先查核，再承諾方案

閱讀 [plan-template.md](references/plan-template.md)，建立精簡、可持續更新的計畫與 evidence ledger。

1. 拆出使用者資料中的「需求／外部事實／對現有系統的描述／假設」。查驗影響方案的主張，不把文件自述當作程式碼事實。
2. 閱讀 repo 指引、實際入口、關鍵 symbol、資料結構、相依版本與相關測試。記錄 commit／工作樹狀態；確認既有行為、可重用元件、難點與限制，避免只靠搜尋摘要或 README 下結論。
   建立 dependency-readiness inventory：必要套件／服務／工具／credential 設定的適用版本與 API 相容性、目標環境、owner、available / missing / unknown、實際查驗證據與所需使用者動作。建立或配置 credential 仍需遵守宿主的逐次確認要求；任務執行授權不等於允許新增持續存取。合約與 log 只記設定名稱／狀態，不寫入秘密值。
3. 對關鍵結論標註 verified / assumed / unknown / contradicted，附 file、symbol、commit 或來源版本與查驗方法。擬新增的路徑明確標成 proposed，未執行的命令不能記成通過。
4. 衝突要說清楚「哪些來源不一致、會改變什麼決策」。使用者最新需求決定目標；實際程式與測試提供現況證據；外部 API 以適用版本的一手資料核實。不要把這些不同用途混成固定來源排名。可由唯讀調查解決的先驗證；已確認的技術發現與仍待決定的問題分開記錄。
5. 對高風險未知安排有時間／範圍界限的 risk spike，寫明要排除的假說、成功證據與停止條件。plan-only 可做唯讀調查或已允許的隔離實驗，不藉 spike 改寫產品或部署。未排除的關鍵可行性風險不得包裝成確定交期。

### 分析確認關卡

以任務及其下游為單位判定關卡。對未解問題記錄 Q-ID、影響的需求／接口／任務、查核證據與解除條件。可查證的技術事實先查核；既有授權內、符合已定契約的例行實作選擇由主代理決定並記錄理由。缺少產品決策、必要授權或會改變驗收／跨任務契約的假設，彙整選項、建議與影響交給使用者，暫停受影響任務及其下游。影響範圍無法界定時，先保守暫停可能受影響的工作並查核，不把未知直接標為無關。

只有具備證據、能說明不共用待定契約或 writer、且不依賴待定結果的任務，才可在原授權內繼續；不得以「低風險」或沉默代替決策。涉及全案目標、共同基礎或整體授權的問題仍阻擋全案。使用者明確要求全部確認後才實作時，遵守該較嚴格範圍。

問題可因查核得到結論、使用者明確決策，或使用者明確接受有界風險／延後驗證／排除範圍而解除特定任務的阻擋；記錄適用範圍、替代驗證、重查時點及尚存缺口。接受風險不會把 unknown 變成 verified，也不能越過必要權限或宣稱未做的驗收已通過。授權內且無阻擋的任務不另加總批准。產品程式碼 spike 同樣受此關卡約束；新問題依相同規則重新評估受影響範圍，已開始的受影響工作依第 4 節停筆程序處理。

## 3. 拆成可交付的任務合約

使用 [task-contract.md](references/task-contract.md) 為每項實作工作建立 task contract；同一規格只存一份，其他任務引用它。

- 以可獨立驗證的成果拆分，而不是只列「做前端／做後端」。假設執行者需要明確提示：每項提供精確上下文、完整的局部 spec、建議修改順序與實作方向、接口／error cases、具體輸入輸出範例、測試斷言與 acceptance criteria。清楚指出不得自行猜測的決策；不要把關鍵設計留給較弱模型，也不要預寫大量實作程式碼或臆測不存在的內部 API。
- 先固定跨任務的資料契約與 ownership，再建立 dependency DAG。明確列出 consumes / produces、依賴的交付物、可並行組別與 critical path。
- 每個檔案或修改區域同時只有一位 writer。共用 schema、路由表、設定、lockfile、產生碼等指定單一 owner 或序列化修改。worktree 可隔離工作樹，但不能消除語意衝突；不可把「不同 worktree」當作無衝突證據。
- 規模過大、需要多個互相獨立驗收條件、或跨越多個 owner 的任務繼續拆分。緊密耦合、不能獨立測試的修改則保持在同一任務。
- 派工前執行 reference 中的 ready-to-dispatch 檢查：材料可存取、接口已定版、依賴已就緒、提示與驗證方法具體，且沒有阻擋本任務的產品／設計選擇。未滿足就補齊，不把「去自己研究」當作實作提示。

## 4. 執行、審查與整合

只有在使用者的任務授權涵蓋執行、本任務的分析確認關卡已通過、前置依賴已就緒時，才啟動實作；實際委派另須確認模型設定。主代理循序執行沿用相同合約、台帳與驗收要求。

1. 每次分派給子代理完整 task contract、必要來源與 repo 指引、base revision、相關使用者指示，以及回報格式；不要假設它能看到父代理對話。主代理持續維護唯一任務台帳與 ownership 表。
2. 子代理只修改自己負責範圍。發現接口不成立、需要越界寫入或依賴改變時，停止受影響寫入並回報，不能自行擴張範圍。合約改版、取消或更換 owner 時，由主代理依序執行：
   - 列出受影響 writer 與下游，停止新派工與成果整合，要求停筆；必要時使用宿主提供的中斷機制。
   - 核對代理及其已啟動工具／背景程序已停止寫入，保存現有 diff、產物與最後使用的合約版本。送出訊息、收到中斷回覆或超時都不等於工具已停止；無法確認時維持 blocked，不派替代 writer 寫同一範圍，也不清空既有修改。
   - 確認停筆後，依分析確認關卡處理新決策，再發布新版合約與 DAG、移交 ownership。新舊版本與受影響驗收保持可追溯。
   - 執行者確認新版與自身範圍後，重新通過 ready-to-dispatch 才恢復。晚到的舊版成果先標 stale，經新版 spec 與相關回歸核對後才可採用；不得直接整合。
3. 收到成果先檢查 spec compliance，再做 code-quality review。審查盡量由未實作該修改的代理分開兩輪完成；若無此能力，由主代理分兩輪審查並揭露限制。主代理若也參與實作，標明 self-review，不能稱為獨立審查；使用者要求獨立審查時，缺口仍待滿足或由使用者明確調整要求。測試證據與實際 diff 優先於子代理自述。
4. 主代理處理整合與衝突，檢查 shared interfaces、migration、設定與生成產物的一致性。所有子任務完成後，主代理必須親自重新做完整最終驗收：逐項核對原始需求、實際 diff、可觀察行為、邊界／錯誤情境及整合結果，並在最後合併狀態執行相關 integration / regression tests；分支各自通過、子代理自行驗收或外部審查報告都不能取代這一步。主代理也實作時如實標明，不能宣稱驗收者獨立於實作者。需要時補上 build、typecheck、lint 或端到端檢查。無法執行的驗證明列缺口，不宣稱完整驗收通過。
5. 執行失敗採有界重試：記錄原因與下一次有何不同。沒有新證據不重複相同失敗；達到任務約定的重試／時間界限，或遇到權限、模型、破壞性操作阻礙時停止受影響步驟並回報。未確認結果前先查狀態，不重複可能已成功的操作。

## 5. 完成或接續

- 只有需求映射、兩輪審查及主代理完整最終驗收都有可檢查的結果，才宣稱相應範圍完成。明列未完成、未測試、已知風險與需要使用者決策的事項；blocked / partial 不能改稱 done。
- commit、build 或測試通過不是部署證據。若本輪包含部署，另核實授權目標環境的實際版本與行為；沒有證據時只報告程式碼／測試狀態。
- 中斷、上下文不足或計畫變更時，更新 plan 中的 resume context pack：目標與授權、版本、已完成成果、正在執行的 owner／狀態、尚未解決的決策及下一個安全動作。恢復時先核對真實工作樹、代理與測試狀態，不以舊摘要直接重做或覆寫他人的變更。
- 計畫交付包含查核結論、矛盾與風險、DAG 與 task contracts；執行交付另外包含變更摘要、實際測試證據及剩餘事項。規劃完成與實作完成分開報告。
