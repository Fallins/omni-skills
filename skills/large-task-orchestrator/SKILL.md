# 大型任務協作

主代理擔任 planner / integrator：使用使用者在目前對話選定的模型與思考程度，負責理解需求、整體規劃、拆解、派工、跨任務決策、審查成果與最終整合驗收判定。不自動改變主對話設定，也不宣稱已驗證無法觀察的模型。子代理在宿主支援且授權允許時，負責有邊界、可驗收的調查、實作、測試或審查；不要只轉交整份需求後等待回報。

## G1 過渡期路由

- 本技能保留既有大型 execute 的單一整合入口與協調保障。只要求計畫時改走 [plan-change](../plan-change/SKILL.md) 並在計畫交付後停止。
- 大型 execute 不要同時啟動另一套 plan-change 流程。若已有 plan-change 產物，先核對其版本、來源和仍有效的決策，再沿用；若沒有，依 plan-change 的 canonical 方法完成一次規劃後，接續本技能的協調與驗收。
- 大型 execute 沿用目前主規劃 session 的 UI 模型／effort，按 plan-change 的 PlannerExecutionCheck 記錄可觀察資訊，不設配置開工閘門。已有 Plan 不因缺少模型或上限證據而重規劃、標 provisional 或阻塞；派工仍需另通過 ready-to-dispatch 並取得必要授權。
- 本技能仍負責本地能力預檢、唯一協調 owner、writer 管理、停止／移交、審查、最終整合驗收及恢復。規劃與 TaskContract 格式共用 plan-change 使用的 [Plan 範本](references/plan-template.md) 和 [TaskContract](references/task-contract.md)，不維護第二套模板。

## 1. 啟動與能力確認

- 辨識本輪目標、範圍與授權。「大型任務模式」或 plan-only 預設只讀取、查核、提出方案；plan-only 由 plan-change 負責並在交付後停止，不進入本協調技能。使用者明確要求規劃並執行時，完成必要查核後依授權繼續，不另加重複批准關卡。具體高風險操作仍遵守有效宿主規則。
- 缺少任務內容、資料或 repo 時，先查找可用來源；只有無法從來源查明且會影響下一步時才問最小必要問題。不得把技能關鍵字當成已安裝全域觸發器。
- 開始前確認可用環境、repo／revision、讀寫權限、驗證工具、代理工具、並行限制，以及委派子任務時宿主能否指定模型與思考程度。只把影響當前步驟的限制標為阻礙；主規劃配置不可觀測不阻擋研究。
- 大型 Plan 依 [plan-change 的 PlannerExecutionCheck](../plan-change/SKILL.md) 直接沿用使用者在目前 session UI 選定的模型與 effort，不為主規劃詢問精確型號、可用上限或 Ultra 額外許可。可觀察值只記作 UI 選定值，不宣稱服務端執行證明；不可觀測就記 unknown／not observable 並繼續已授權工作，不要求 fallback。此紀錄不套用 light，也不授權另開任務或派工。
- 子任務的模型推薦沿用 [plan-change 的委派角色模型推薦](../plan-change/SKILL.md)，這是同一規則在派工時的約束，不是第二套政策，也不新增協調者或額外驗收輪。區分推薦、使用者要求、工具接受設定與可觀察型號；不設固定模型偏好，也不聲稱已切換。實際委派前仍依本次使用者授權與宿主規則確認模型／effort、執行範圍及必要許可，不能以主規劃 UI 選定值代替。推薦不是取得額外額度、啟動外部任務或其他動作的授權。不為每次能力檢查另設重複確認關卡。本技能不因模型分工把小型工作升級成大型任務。
- 只有確實要委派時才確認委派所需設定。依宿主實際能力分開處理，不混成一種：
  - **A. 可指定模型／思考程度**：對需求明確、範圍可界定、驗收具體的實作切片，主動評估並優先考慮能力足夠且成本較低的模型，或適當的較低思考程度。先考量適任、工具能力與完成品質，再比較成本與返工風險。這是有條件的預設，不是強制所有實作降階，也不是略過必要測試、審查或驗收。權限、資料安全、migration、並發、跨 repo 契約、重要架構或高度不確定的工作，不得只因任務看起來小就降階。較低階模型不保證便宜，也不保證勝任；不寫死模型品牌、等級或價格排名。只有工具與平台提供足夠證據時才說已使用某設定。
  - **B. 可派子代理但不能指定模型或思考程度**：授權與宿主規則允許時，可以使用宿主實際提供的子代理。明說無法控制的項目，以及可能繼承或使用的設定；只根據可觀察證據描述，不宣稱成本已降低。使用者把特定模型訂為必要條件而無法達成時，暫停受影響部分並回報。
  - **C. 沒有可用子代理，或工具／名額不足**：使用者只要求成果、未指定必須委派且授權允許時，由目前主代理按相同 TaskContract 與任務範圍循序完成實作與必要驗證，並說明無法採用模型分工，以及成本與時間因此不確定。如實記錄執行者；不因此擴大權限、略過驗證或宣稱獨立審查。使用者明確要求必須委派或指定執行者而無法滿足時，停下受影響部分並回報。
  - **D. 能建立任務但無法確認實際模型、價格或是否成功啟動**：先核對可觀察狀態。狀態不明就如實回報，不憑預設值或 tool-accepted 宣稱成功，也不重複啟動可能已成功的任務。沒有成本資料就標未知，不編造節省金額。
- 遇到規格、授權、驗收或跨任務契約未知時，套用 Plan 的分析確認關卡；可查核的技術事實先查，必要產品決策或權限缺口只阻擋受影響工作。

## 2. Plan 與研究的唯一來源

本技能被選作大型 execute 入口時，Plan 由本技能單一 owner 負責；沿用目前 session UI 模型／effort，保留不阻擋研究的 PlannerExecutionCheck 配置紀錄，再依 plan-change 的研究、矛盾查核、架構、DAG、TaskContract、委派角色推薦與完成門檻執行。既有 Plan 依範圍、證據新鮮度、契約、依賴與驗收核對，不因缺少主規劃配置證據而失去 ready 狀態。派工另須通過 ready-to-dispatch 及必要授權。不要把相同任務再交給另一位 planner，也不要重複已讀且仍新鮮的研究。完整計畫欄位見共用的 [Plan 範本](references/plan-template.md)。

計畫要區分 plan-complete 與 ready-to-dispatch。只要求規劃時交付前者及尚未 ready 的原因後停止；明確要求規劃並執行時，也只有通過本次分析確認關卡、授權涵蓋且依賴就緒的任務才可進入執行。完整 TaskContract 欄位見共用的 [TaskContract](references/task-contract.md)。

## 3. 分工與 TaskContract

所有子任務使用共用 TaskContract，先固定跨任務資料契約與 ownership，再建立 dependency DAG。每個檔案或修改區域同時只有一位 writer；共用 schema、路由表、設定、lockfile 和生成碼要指定單一 owner 或序列化修改。不同 worktree 不代表語意上沒有衝突。

派工前核對 ready-to-dispatch：材料可讀、接口已定、依賴和環境就緒、owner 清楚、驗證方式具體，且沒有阻擋本任務的未決產品／授權選擇。未滿足就補 Plan 或標 blocked，不把「去自己研究」當作實作提示。需求明確、範圍可界定、驗收具體的實作切片，才適用上面的有條件成本預設；關鍵設計決策留在 TaskContract，不交給執行者猜，也不為每個切片另建文件。

## 4. 執行、審查與整合

只有在使用者的任務授權涵蓋執行、本任務的分析確認關卡已通過、前置依賴已就緒時，才啟動實作；實際委派另須確認模型設定。主代理循序執行沿用相同合約、台帳與驗收要求。

每個實作切片可沿用 [implement-change](../implement-change/SKILL.md) 的新功能／BUG／重構及設計到程式 playbook；驗證沿用 [verify-change](../verify-change/SKILL.md) 並保存 VerificationReceipt；規格符合與程式風險審查沿用 [review-change](../review-change/SKILL.md)。[coordinate-work](../coordinate-work/SKILL.md) 是可重用的生命週期方法，不是第二個整案協調入口：本技能仍是唯一 coordinator，保留停止／移交、writer ownership、review 排程與主代理最終整合驗收，不再啟動重複 DAG、任務台帳或派工流程。設計批准後回 Plan 更新 DesignImplementationMap 與 TaskContract，再按版次實作；不得略過使用者審核直接從原型寫程式。

1. 每次分派給子代理完整 task contract、必要來源與 repo 指引、base revision、相關使用者指示，以及回報格式；不要假設它能看到父代理對話。主代理持續維護唯一任務台帳與 ownership 表。
2. 子代理只修改自己負責範圍。發現接口不成立、需要越界寫入或依賴改變時，停止受影響寫入並回報，不能自行擴張範圍。合約改版、取消或更換 owner 時，由主代理依序執行：
   - 列出受影響 writer 與下游，停止新派工與成果整合，要求停筆；必要時使用宿主提供的中斷機制。
   - 核對代理及其已啟動工具／背景程序已停止寫入，保存現有 diff、產物與最後使用的合約版本。送出訊息、收到中斷回覆或超時都不等於工具已停止；無法確認時維持 blocked，不派替代 writer 寫同一範圍，也不清空既有修改。
   - 確認停筆後，依分析確認關卡處理新決策，再發布新版合約與 DAG、移交 ownership。新舊版本與受影響驗收保持可追溯。
   - 執行者確認新版與自身範圍後，重新通過 ready-to-dispatch 才恢復。晚到的舊版成果先標 stale，經新版 spec 與相關回歸核對後才可採用；不得直接整合。
3. 審查固定 revision 的 spec compliance 與 code quality；一般可由一份報告涵蓋兩軸，不強制兩輪或第二人。不能僅以模型階級推定審查品質或獨立性。使用者、團隊或專案明確要求獨立審查時必須滿足，否則保留缺口，不得自行放寬或假稱已滿足。實作者自行審查標明 self-review，不稱獨立；測試證據與實際 diff 優先於自述。修正後複查受影響部分；已確認修復的 finding 無新證據不重開，低風險問題集中列管，不為每項小修重啟整案。
4. 主代理負責最終整合判定，處理衝突並核對 shared interfaces、migration、設定與生成產物；逐項確認全部必要需求及正常、邊界、錯誤和整合情境在最終整合版本有適用的驗收證據。依 [verify-change](../verify-change/SKILL.md) 核對並沿用適用的同最終版本或同產物證據，不要求主代理親自重跑全部；跨 revision 只有具體差異及依賴影響分析足夠時才考慮沿用。針對受影響項、缺失證據與新增整合風險補驗，分支各自通過不證明跨切片流程通過。必要時執行 integration／regression、build、typecheck、lint 或端到端檢查；核心流程、權限、資料安全、重要回歸及專案強制 gate 不降級。主代理也實作時如實標明；必要驗證無法完成要列缺口，不宣稱完整通過。
5. 執行失敗採有界重試：記錄原因與下一次有何不同。沒有新證據不重複相同失敗；達到任務約定的重試／時間界限，或遇到權限、模型、破壞性操作阻礙時停止受影響步驟並回報。執行者因能力不足、重複失敗或風險高於預期而卡住時，先說明問題並保存成果，只對受影響工作重新評估；授權仍在且宿主支援時，可升級模型、調整拆分或交回主代理，不把同一低價嘗試無限重跑。未確認結果前先查狀態，不重複可能已成功的操作。

## 5. 完成或接續

- 只有全部必要需求、適用的驗收證據及所需審查均有可檢查的結果，主代理才可依 [CompletionDecision](../../docs/contracts/completion-decision.md) 判定相應範圍完成。明列未完成、未測試、已知風險與需要使用者決策的事項；blocked / partial 不能改稱 done。
- commit、build 或測試通過不是部署證據。若本輪包含部署，另核實授權目標環境的實際版本與行為；沒有證據時只報告程式碼／測試狀態。
- 中斷、上下文不足或計畫變更時，更新 plan 中的 resume context pack：目標與授權、版本、已完成成果、正在執行的 owner／狀態、尚未解決的決策及下一個安全動作。恢復時先核對真實工作樹、代理與測試狀態，不以舊摘要直接重做或覆寫他人的變更。
- 計畫交付包含查核結論、矛盾與風險、DAG 與 task contracts；執行交付另外包含變更摘要、實際測試證據及剩餘事項。規劃完成與實作完成分開報告。
